# 第二版 Roadmap

本文件記錄第二版網站規劃。第二版不是帳號系統或通知系統，而是把第一版查詢網站升級成更能追蹤價格、判斷資料可信度、比較商品與維運公開服務的版本。

## 目標

- 讓使用者能看懂商品價格變化，而不只看到目前價格。
- 讓使用者能快速找到近期價格異動商品。
- 提升來源連結、圖片與商品資料的可信度。
- 建立正式資料 / 圖片更正與移除處理機制。
- 在不建立帳號的前提下，加入輕量商品比較與規格輔助資訊。
- 讓公開服務有足夠的 crawler、資料流與網站監控能力。

## 非目標

第二版不做：

- 使用者帳號、登入、註冊或 OAuth。
- 收藏清單、追蹤清單或 watchlist。
- 個人價格提醒。
- 使用者通知中心。
- 使用者導向 Discord bot 或私訊通知。
- 使用者上傳資料、留言、評價或個人化推薦。
- 跨網站比價或多資料來源整合。
- 購物車、下單、自動購買或代購流程。

若未來真的需要帳號、提醒或使用者通知，必須另開產品與資安設計，不從第二版自然延伸。

## 進入條件

- 第一版網站已能穩定公開運行。
- CoolPC crawler 能持續取得主要分類資料，且疑似攔截、parse error 與 stale 狀態能被辨識。
- 商品圖片快取、備份、搬遷與移除流程已完成第一版公開前最低要求。
- Production smoke、source status 與基本安全 headers 已可驗證。
- 文件、部署設定與實作狀態沒有明顯脫節。

## 第二版範圍

### 1. 價格歷史

目標：讓商品詳細頁可以呈現價格走勢。

範圍：

- 商品價格歷史 API。
- 商品詳細頁價格走勢圖。
- 近 7 / 30 / 90 天與全部時間的最低價、最高價、均價與價格變化。
- 價格走勢圖提供少量可調整口徑，已先支援時間範圍與 hover / tap tooltip。
- 價格 / 漲跌幅模式、觀測點來源切換、Y 軸縮放、最低 / 最高 / 目前標記切換留待後續評估；若會讓 UI 變複雜，應延後或取消。
- 歷史最低價或近期低點提示。
- 無歷史資料、資料不足與商品 inactive 狀態處理。

目前狀態：

- 已完成第一輪：價格歷史 API、商品詳細頁價格走勢圖、7 / 30 / 90 / 全部時間範圍、期間變動卡、區間摘要卡、tooltip、變價紀錄分頁、價格未變時的目前價格確認點。
- 已整理價格走勢 UI / CSS 結構，避免單一 `price-history.css` 過度膨脹。
- 尚未完成：歷史低點 / 近期低點提示、價格 / 漲跌幅模式、觀測點來源切換、Y 軸縮放與額外標記控制。

完成條件：

- 價格未變時不產生誤導性重複點。
- raw snapshot cleanup 不影響價格歷史查詢。
- 歷史圖不暗示來源價格更新頻率保證。
- 價格走勢圖控制項保持輕量，不做股票軟體式分析介面。
- 第二版價格歷史不包含自訂日期區間、多商品疊圖、均線、技術指標或多圖表樣式切換。

### 2. 價格變動探索

目標：讓首頁不只依目前價格排序，也能找出值得注意的價格變化。

範圍：

- 最近降價。
- 最近漲價。
- 接近歷史低點。
- 近 7 / 30 天變動幅度。
- 價格變動排序與篩選。

目前狀態：

- 已完成第一輪：首頁商品列表顯示近 30 天價格變動欄位，無變動以 `-` 顯示；支援近 30 天降幅最大與近 30 天增幅最大排序。
- 尚未完成：接近歷史低點、近 7 天變動、價格變動篩選與更完整的資料不足呈現。

完成條件：

- 變動計算有明確時間窗與資料不足處理。
- 首頁查詢仍維持 table-first 掃描體驗。
- API response 不暴露 crawler internal details。

### 3. 商品連結健康檢查

目標：避免網站長期顯示已失效或不適合導出的來源連結。

範圍：

- 低頻連結健康檢查。
- 原價屋查看 / 購買連結與產品介紹連結狀態欄位。
- 失效、疑似 redirect 異常、暫時失敗與待重試狀態。
- UI 隱藏或低干擾標示失效連結。
- backoff 與 request rate 控制。

完成條件：

- link checker 不在使用者 request lifecycle 執行。
- 單次失敗不立即移除連結。
- 來源站異常時不造成大量重試。

目前狀態：

- 已完成第一輪：`product_link_health` schema / migration、`ops:product-links:check` 低頻檢查命令、dry-run / live confirmation、可選批次上限、10-20 秒 request delay、48 小時 stale window、連續 404 / 410 失敗門檻、商品詳情 API / UI 低干擾健康提示。
- 尚未完成：主機端排程化、部署後 live check 驗證、redirect 異常細分、與正式更正 / 移除流程的略過規則整合。

### 4. 正式更正 / 移除流程

目標：把第一版 GitHub Issues 臨時入口升級成可維運的人工處理流程。

範圍：

- 正式聯絡信箱或聯絡頁。
- 商品、圖片、來源連結的人工移除 / 停用紀錄。
- 延伸第一版公開前的資料庫永久 override / removal table。
- 補強圖片快取清理命令、crawler / image backfill / link checker 略過規則與操作紀錄。
- 操作紀錄與回復流程。

完成條件：

- 合理移除請求處理後，網站不再顯示被移除資料或圖片。
- 後續 crawler 不會自動復原被移除內容。
- 處理流程不需要公開管理後台。

### 5. 輕量規格副標

目標：從商品名稱產生低風險、低干擾的輔助資訊，改善掃描與比較體驗。

範圍：

- 依分類萃取可相對穩定的副標，例如容量、瓦數、顯存、介面或尺寸。
- 規格副標只作為輔助顯示，不作為完整規格資料庫。
- 對低信心結果不顯示副標。
- 建立 fixture 與人工抽樣驗證流程。

完成條件：

- UI 不把副標包裝成官方規格。
- 低信心或無法解析時不顯示，不製造錯誤資訊。
- 不在第二版一開始承諾完整規格篩選。

### 6. 商品比較

目標：在不建立帳號的前提下提供一次性商品比較。

範圍：

- 使用 URL state 或 client-side state 保存比較候選。
- 比較目前價格、分類、廠商、來源狀態、價格更新時間、價格歷史摘要與可用規格副標。
- 支援分享比較頁 URL，但不保存個人清單到伺服器。

完成條件：

- 不需要登入、收藏或伺服器端使用者資料。
- 比較表不宣稱效能、相容性或購買建議。
- 手機版比較表仍可閱讀，不造成水平內容失控。

### 7. 營運監控

目標：讓公開服務能被維護，而不是只靠人工偶爾查看。

範圍：

- crawler 連續失敗、suspected block、parse error 激增通知。
- source status 歷史摘要。
- production smoke test script。
- product image backfill / cleanup 檢查。
- raw snapshot retention 檢查。
- API error 與 rate limit 觀察。

完成條件：

- 監控先以管理者 / 維運者為對象，不做使用者通知。
- 異常訊息能指向可執行的 runbook。
- 不把監控資料公開成使用者可查詢的內部細節頁。

## GitHub Release 策略

網站型專案不需要每次部署都建立 GitHub Release。Release 應只標記可回溯的公開里程碑：

- 第一版公開穩定後建立 `v1.0.0`。
- 第二版正式上線後建立 `v2.0.0`。
- 重大修補再使用 patch version，例如 `v2.0.1`。

Release notes 應包含主要功能、migration / deployment 注意事項、驗證過的 commit SHA、已知限制與 production 網址；不包含 `.env`、資料庫 dump、raw snapshot、商品圖片快取或任何私有資料。
