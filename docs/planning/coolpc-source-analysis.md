# 原價屋資料來源初步分析

本文件記錄 PartsRadarTW 對原價屋公開頁面的初步觀察，目的是協助後續 crawler、資料模型與內容驗證設計。這不是正式實作規格；已確認、延後與待決事項仍以 [decision-log.md](decision-log.md) 為準。

觀察日期：2026-05-25

## 觀察來源

本次只檢查少量公開頁面，先確認第一版資料流需要的基本結構。依照舊專案經驗與目前觀察，第一版 crawler 以分類總覽頁作為抓取來源：

- `https://www.coolpc.com.tw/eachview.php?IGrp={分類編號}`

## 編碼與抓取注意事項

原價屋頁面目前以 Big5 編碼回傳，crawler 應明確處理編碼轉換，避免商品名稱、分類名稱或特殊符號解析錯誤。

HTTP 狀態碼不能作為唯一成功依據。即使狀態碼為 200，仍需要確認頁面內容是否包含預期的商品列表結構。若內容缺少必要結構，應標記為非預期內容或疑似攔截，不應進入正式商品更新流程。

## `eachview.php?IGrp={分類編號}` 抓取來源

`eachview.php?IGrp={分類編號}` 入口符合 PartsRadarTW 第一版需要的資料形狀：

- 可以依原價屋分類分批抓取，範圍較小。
- 商品標題與價格分開呈現，較容易解析。
- 商品區塊中可取得 `iBuy` token，較適合作為來源商品識別基礎。

`eachview.php?IGrp=4` 是處理器 CPU 分類總覽頁。初步觀察到的特徵：

- 頁面標題可作為內容驗證線索之一。
- 每個商品區塊包含隱藏的 `iBuy` token、商品標題與價格區塊。

後續正式實作前仍應抽查第一版目標分類，確認其他 `IGrp` 頁面是否都具備相同商品區塊與 `iBuy` token。

## 第一版分類對應

依照目前「先處理組電腦必要硬體」的產品邊界，原價屋分類可先對應如下：

| PartsRadarTW 第一版分類 | 原價屋分類編號 | 原價屋分類名稱 |
| --- | --- | --- |
| CPU | `IGrp=4` | 處理器 CPU |
| 主機板 | `IGrp=5` | 主機板 MB |
| 記憶體 | `IGrp=6` | 記憶體 RAM |
| SSD | `IGrp=7` | 固態硬碟 M.2 / SSD |
| HDD | `IGrp=8` | 2.5 / 3.5 傳統內接硬碟 HDD |
| 散熱器 | `IGrp=10` | 散熱器 / 散熱墊 / 散熱膏 |
| 顯示卡 | `IGrp=12` | 顯示卡 VGA |
| 機殼 | `IGrp=14` | CASE 機殼 |
| 電源供應器 | `IGrp=15` | 電源供應器 |

水冷分類 `IGrp=11` 可等散熱器資料整理時再決定是否納入第一版。機殼風扇與機殼配件 `IGrp=16` 屬於擴充分類，暫時不列為第一版必要硬體。

## 商品識別建議

商品主檔仍應使用內部 UUID 作為資料庫主鍵；crawler 判斷同一個原價屋商品時，應使用來源鍵 `source_item_key`。

若 `eachview.php` 各分類頁都能取得穩定的 `iBuy` token，建議第一版 `source_item_key` 使用下列概念：

```text
coolpc:igrp:{IGrp}:ibuy:{iBuyToken}
```

這個做法的優點：

- 不依賴商品名稱，降低名稱微調造成歷史資料斷裂的風險。
- 不依賴價格，避免價格變動導致商品被誤判為新商品。
- 不依賴每次抓取才產生的 UUID。
- 保留分類編號，方便避免不同分類出現相同 token 時互相衝突。

若某些商品沒有 `iBuy` token，第一版不匯入正式商品資料，但應保留原始商品名稱、分類、raw snapshot 與解析紀錄，方便後續人工檢查或 parser 修正。

## 內容驗證建議

第一版 crawler 可先用保守規則判斷頁面是否為預期內容。

`eachview.php?IGrp={分類編號}` 可檢查：

- 頁面標題包含對應分類名稱。
- 頁面包含商品標題區塊。
- 頁面包含價格區塊。
- 頁面包含可產生 `iBuy` 連結的 token。

若 HTTP 200 但缺少上述必要結構，應標記為 `suspected_block` 或 `invalid`，不應更新 product、price snapshot 或 current price。

## 解析注意事項

- 價格可能以 `$` 或 `NT` 形式出現，parser 應先正規化成整數金額與固定幣別。
- 原價屋頁面中的顏色、促銷標記或樣式 class 可先視為呈現資訊，不應進入商品識別。
- 停用選項、分類說明與促銷文字需要排除，避免被誤寫成商品。
- 商品名稱應保留原文作為顯示欄位；正規化名稱只用於搜尋或比對輔助。
- 原始 URL 應避免保存帶有 `PHPSESSID` 的版本。

## 後續驗證重點

後續正式寫 crawler 前，應再抽查第一版目標分類的 `eachview.php?IGrp={分類編號}` 頁面，確認是否都具備 CPU 分類頁觀察到的商品區塊與 `iBuy` token。

若未來實際遇到原價屋攔截頁，應保存 raw snapshot 並補充其內容特徵，讓內容驗證規則能穩定排除 HTTP 200 但非商品資料頁的情況。
